# 群调度设计：可选 Jev、统一 Leader 与可恢复活动

> 初始架构设计记录，含后续演进项。当前桌面实现以 [群协作文档](group-collaboration.md) 和 [按配置决策验收](group-policy-validation.md) 为准：设置为“默认 / 决策模型”两种模式，报数、@ 消息、leader 选择与故障处理统一经过该模式；本文的 rules/hybrid 模式表及分布式选举等内容不代表已实现能力。


状态：本地单账号版本已实现；下文保留完整设计提案。实际实现和边界见 [群协作说明](group-collaboration.md)，实测结果见 [验证记录](group-orchestration-validation.md)。调研日期：2026-09-23。

本次按用户允许的范围，支持一个真人与自己的多个 Agent。跨设备租约、多真人权限、通用 DAG 编辑器、独立 rules 配置档及成本报表仍属于后续设计；当前采用单进程调度、持久化步骤日志和游戏状态机，不宣称实现了下文全部跨账号协议。

目标：普通群聊能判断零人、单人或多人回复；长活动能跨消息、私信、超时和重启持续推进；使用 Jev 与不使用 Jev 共用协议和验收标准。

## 1. 核心决策

采用「按权限广播消息 + Leader 统一分配 + 执行器独占领取任务」。广播和抢占属于不同层，不需要二选一。

| 层次 | 规则 | 责任方 |
| --- | --- | --- |
| 消息可见性 | 群消息对群成员可见；私信仅授权接收者可见 | 消息存储、权限检查 |
| 语义判断 | 是否需要 Agent、谁适合、是否需要复杂计划 | Jev 或现有 LLM controller |
| 任务规划 | 分解任务、依赖、交接、汇总 | Leader 的规划会话 |
| 发言与执行 | 校验计划、发资格、顺序、重试、取消、持久化 | 确定性调度器 |
| 活动规则 | 游戏阶段、合法行动、投票、胜负 | 活动状态机 |

Leader 是群中的组织角色；Jev 是可替换的判断后端；调度器是程序。Leader 可以用现有模型发言，后台通过 Jev 做简单分流。不能让一个模型同时成为唯一状态存储和最终执行权威。

## 2. 现有实现与缺口

根据当前工作区代码和文档：

- `src/shared/bot/group.ts` 已有 `GroupDecision`、`single/parallel/sequential/none`、显式提及、模型控制器、私信触发和失败替换。
- `src/main/runtime.ts` 已为 controller 使用独立会话，尝试其他成员接替不可用 controller，并展示原 Leader 不可用时的接管状态。
- `Conversation.leadAgentId` 已保存用户指定的 Leader；默认取首个有效成员。当前运行中的接管不等于持久化选举或跨设备互斥。
- `privateMessages.ts` 已分离公私消息；成员只获得自己收发的私信，controller 只看到信封。已有隐私处理应复用。
- `GROUP_MAX_TURNS = 16` 是一次调用的执行上限；达到后要求用户再发消息。循环里的待执行队列和完成记录不足以作为长活动恢复日志。
- 私信送达当前可以触发接收成员执行；纯身份通知需要新增不触发行动的语义。
- 当前失败替换会尝试其他群成员。游戏玩家、判官不能这样任意替换，否则改变身份或泄露秘密。
- 远程共享群使用单独的服务端任务 claim 协议、owner 权限和结果 outbox；现有跨账号 Agent 调用回复公开，尚不支持游戏的秘密身份投递。不能因为本地游戏成功就宣称跨账号群也支持。

本设计沿用已有控制器和消息机制，新增持久化调度协议与活动层。

## 3. 发言规则

### 3.1 路由优先级

按顺序处理，每条事件最多提交一个有效路由决策：

1. 检查身份、群成员资格、访问范围、重复事件和会话取消状态。
2. 用户明确的停止、暂停、换 Leader 等控制动作进入对应程序路径。
3. 若消息回复某个待完成任务、游戏发言槽或投票请求，优先归入该活动，不重新启动群聊分流。
4. 真人明确只发给真人、禁止 AI 回复，且没有未完成的相关 Agent 指令：`ignore`。
5. 明确 @Agent：提交给指定成员；仍受当前活动、权限和发言槽约束。@多人默认按提及顺序；明确独立的任务可并行。@真人与 @Agent 混合时，仅给明确被要求行动的 Agent 建任务。
6. 无显式对象：统一经 Leader 的决策后端判断。语境明确的“你继续”可以指向前一位成员，但不能把所有新消息黏在上一位发言者身上。
7. 不确定则用 LLM controller 进一步判断；确实缺少信息才让 Leader 问一个问题，然后进入 `wait`。

“大家每人讲个笑话”可以并行；“A 提方案，B 挑问题，C 总结”必须按依赖顺序；“小王，晚上几点到？”可以零 Agent 回复。活动中出现离题消息单独路由，不改写当前游戏阶段。

### 3.2 Leader 如何 @ 人

默认由 Leader 身份展示派发，例如：

> @阿喵 先分析问题；完成后 @豆博士 补充；最后 @阿喵 汇总。

这条消息由已验证的任务计划渲染，与任务、发言资格在同一事务中提交。固定格式的派发无需额外调用生成模型。用户已明确 @ 单人时可直接展示目标成员正在回复，避免多一条确认。

程序执行依赖结构化 `assigneeId / dependsOn / slotId`，不靠重新解析这段展示文案。单纯引用、代码块里的 @ 或讨论“请 A 当 Leader”不能产生执行资格。

迁移期间保留旧版 @handoff 和 `[[private:...]]`，但只把它们解析成候选动作，再做权限、重复、活动阶段检查。只有运行中任务允许的交接才能创建下游任务；不能让任意群消息伪造派发。

### 3.3 广播、监听与领取

- 所有成员的客户端可以同步其可见消息；不为每条消息唤醒全部成员的 LLM。
- 被派发的成员执行时，从消息游标补齐必要的公开上下文，再拼接自己的私信与任务上下文。
- 同一任务只有一个 owner 设备能通过原子条件更新领取。多人回复意味着多个任务各自领取，不是整群永远只能有一个任务运行。
- 顺序任务在前序结果提交后才启动，保证后者确实看到了前者结果；不能先并行生成、再只调整显示顺序。
- 并行只用于独立工作，限定并发数量；公开发言按预定顺序提交，或活动明确允许时按完成顺序提交。投票可以并行收集但统一揭示。
- 可选“自荐模式”允许订阅了特定事件的成员申请任务，Leader 最终选择；默认关闭，不以模型响应速度决定谁最适合。

## 4. 统一决策协议与 Jev

### 4.1 Jev 的位置

[官方介绍](https://docs.typesafe.ai/introduction)把 Jev 定义为结构化判断模型：Choice 单选、Noul 返回肯定概率、Score 按给定等级评分。同一请求的多个问题互相独立，不能把它当成自动执行多步规划的模型。

建议每次传入最小的公开状态：当前消息、明确回复对象、最近相关对话、授权成员能力、当前可执行槽和已完成任务摘要。不要传整个群历史，更不要传游戏身份、私信正文或其他会话历史。

| 判断 | 形式 | 程序如何使用 |
| --- | --- | --- |
| 当前消息期待 AI 介入吗 | Noul | 区分介入、低把握升级、无需介入 |
| 需要哪种处理 | Choice | 无需回复、单人、多人独立、多人依赖、开活动、需澄清 |
| 单人请求最适合谁 | Choice | 在合法候选成员和“无法确定”中选一个 |
| 多人请求需要某成员吗 | 每个候选一个 Noul | 在代码里合成成员集合，不要求 Choice 返回数组 |
| 两项已提出的工作存在先后关系吗 | 可选 Noul | 提供规划参考，不代替 DAG 验证 |

同批问题可以预判，但程序必须检查答案一致性：无需回复时忽略成员选择；多人集合为空、矛盾结果、复杂依赖都升级 LLM planner。任意顺序和新任务说明由规则或 LLM 生成，Jev 不负责生成这些字段。

群很大时先以权限、可用性、能力标签和任务相关性筛选候选，明确 @ 和待执行槽成员必须保留；候选不足时扩大范围或升级规划，不能在错误的小集合里强行选一个。官方 Choice 最多 255 个选项。[请求格式](https://docs.typesafe.ai/api)

### 4.2 接入接口

优先封装单独的 `JevDecisionProvider`，在 Electron main / 服务端调用：

```text
POST https://openrouter.ai/api/v1/systemone
Authorization: Bearer <OpenRouter key>
{ model, state, questions }
→ { model, answers, usage, ... }
```

OpenRouter 官方还提供 `/api/alpha/decisions`。推荐本项目先采用有兼容文档的 System One 接口；不能把 Jev 直接加入聊天模型列表后沿用 `chat/completions`。

System One 支持 `jev-1.13` 映射到 `typesafe/jev-1.13`，`jev-latest` 映射到 `~typesafe/jev-latest`。上线配置固定已验证的模型版本，记录响应的实际模型 ID；latest 用于评估升级。适配器做响应 schema 校验，按请求保存使用量和成本，不把供应商的能力假设散入调度逻辑。[OpenRouter 接入说明](https://openrouter.ai/docs/guides/community/typesafe-sdk)

### 4.3 兼容三种模式

| 配置 | 模型路径 | 保障 |
| --- | --- | --- |
| `llm` | 明确规则 → 现有 LLM controller | 默认兼容，无 Jev 也完整支持自动活动 |
| `hybrid` | 明确规则 → Jev → 必要时 LLM planner | 可选启用，降低简单决策的延迟和调用成本 |
| `rules` | 仅明确 @、已有任务、已注册活动状态机 | 模型决策均不可用时的有限降级，不承诺理解任意含糊请求 |

这里的 rules 仅指路由后端。玩家、成员正常发言仍需要可用的生成模型；所有生成模型都失效时应暂停活动。

Jev 超时、429、5xx、格式错误、答案矛盾或低把握，转 LLM controller；连续故障熔断，冷却后探测恢复。认证错误直接标记配置不可用，不逐消息重试。两个后端不能各自发布一份任务。

可以先用 Noul ≥ 0.8 介入、≤ 0.2 不介入、中间升级；Choice 结合 top-1 概率和前两名差距。以上只是待评估的初始参数，不是模型保证。静默误判会漏掉用户请求，需要单独优化召回。Choice 的 confidence 不是“这次一定正确的概率”，不能与 Noul 用同一阈值解释。[置信度说明](https://docs.typesafe.ai/confidence)

数学、计票、时间比较、身份权限和终止条件始终由代码计算。Jev 官方明确列出了数值、多层推断、大量无关上下文等弱项。[已知局限](https://docs.typesafe.ai/model-jaggedness/jev-1.13)

## 5. 持久化任务与事件

以下为建议的数据契约；不是现有类型的声明：

```ts
type RoutingOutcome =
  | { kind: 'ignore'; reason: 'human_only' | 'no_action' }
  | { kind: 'wait'; waitFor: 'human' | 'approval' | 'device'; requestId: string }
  | { kind: 'dispatch'; planId: string; taskIds: string[] }
  | { kind: 'finish'; workflowId: string; resultId: string }

interface ScheduledTask {
  id: string
  groupId: string
  topicId: string
  workflowId: string
  triggerEventId: string
  planVersion: number
  assigneeId: string
  dependsOn: string[]
  slotId?: string
  audience: { kind: 'group' } | { kind: 'private'; recipientIds: string[] }
  status: 'pending' | 'running' | 'waiting' | 'succeeded' | 'failed' | 'cancelled'
  attempt: number
  leaderEpoch: number
  claimToken?: string
  leaseUntil?: number
  idempotencyKey: string
  deadlineAt?: number
  resultId?: string
}
```

单人是一个任务；多人顺序是依赖链；多人独立是无依赖任务集；汇总是依赖全部必要结果的任务。游戏使用已确定的阶段模板生成任务，不让 Leader 每轮重新发明流程。

保存 `GroupEvent`、`Workflow`、`Plan`、`ScheduledTask`、`LeaderLease`、`Outbox`；游戏另存 `GameSession`、`PrivateState`、`Vote`。状态转移、下一步任务和待发布消息必须事务性提交，使用唯一约束去重，outbox 发布可重试。

事件包括 `message.created`、`task.started/progress/completed/failed`、`private.delivered`、`human.action`、`deadline.expired`、`leader.changed`。新的消息、任务完成和持久化定时器都能唤醒调度，不能只靠人发“继续”。

Agent 必须通过运行时上报：开始、阻塞、失败、完成；进度按有意义的检查点或限频更新。心跳由执行器发，不要求 LLM 输出“我还活着”。controller 获得必要状态与结果引用；只有异常、决策点和最终结果默认进入公开聊天。

`succeeded` 表示输出已验证并保存，不是 Agent 在正文里说“完成了”。被阻塞任务要记录等待对象；投票或发言不合法可以限次纠正，再按预定规则超时处理。

### 5.1 冲突和恢复

- 输入事件以 `groupId + eventId` 去重；同一事件的计划以版本和唯一键防止重复提交。模型结果返回后检查状态版本，过期则重新判断，不能覆盖新消息的决定。
- 新任务默认排队；明确取消、改目标等操作递增 workflow 版本，使旧任务结果失效。活动中的合法玩家输入按活动 ID 和动作 ID 关联。
- 同一活动的状态转移串行提交；独立话题可并发。游戏拥有自己的发言序列，普通闲聊不能抢走游戏槽。
- 至少一次事件投递 + 幂等提交实现单次可见结果，不承诺模型只调用一次。已执行的外部工具副作用必须单独有操作幂等键；执行结果不明时进入待核对状态，不盲目重跑。
- 自动推进使用每次唤醒的计算预算、活动总预算、无进展计数和截止时间。短暂让出执行后持久化自动续调；达到活动预算时明确暂停，不能冒充游戏胜负。
- `ignore` 只代表这条消息无需动作；`wait` 代表活动尚未结束；`finish` 必须有终态及结果。不能再用一个 `none` 同时表达三种状态。

## 6. Leader 冗余与选举

区分三种故障，分别恢复：

| 故障 | 处理 |
| --- | --- |
| Jev / controller 模型不可用 | 同一 Leader 身份切换后端，通常无须选举 |
| Leader Agent 无法继续组织 | 从合格备用主持角色中接管，变更 term/epoch |
| 持有调度工作的进程 / 设备退出 | 共享存储上的租约到期，由其他可用执行器恢复 |

本地群只有一个 Electron main，先用进程内串行执行 + SQLite 持久化恢复即可。应用退出且无在线托管进程时无法在后台继续，重启后恢复。跨账号共享群由服务端作为唯一租约权威，不让不同桌面自行判断谁当选。

候选顺序：用户指定备用 Leader → 符合资格的其他主持者按稳定优先级 → 稳定 ID 打破平局。资格必须包含权限、在线状态、模型健康、可接管角色及活动冲突；同供应商一起故障时应考虑不同后端。无需让多个 LLM 投票选举。

共享群可先采用 5 秒心跳、20 秒租约作为初始配置，使用服务端时间，按实际网络状况调优。通过原子 compare-and-swap 获得 `leaderEpoch + 1`，事务里写新 holder；没有获得租约者只观察、不派发。普通 presence 在线状态不等于调度租约。

所有派发、任务领取和结果提交都必须校验当前 epoch 与 claim。新 Leader 恢复已完成结果、待办、截止时间；对旧任务显式选择沿用或取消。沿用时事务性换发当前 epoch 的 claim，再接受结果；旧 Leader 和旧 claim 的迟到结果一律拒绝。长耗时副作用在真正执行前也需检查有效资格。

恢复后的旧 Leader 不自动抢回当前活动。没有合格备用主持者则暂停并说明原因。

## 7. 游戏必须有独立活动层

### 7.1 判官、玩家和秘密

群 Leader 负责组织；游戏判官是独立服务身份和会话；玩家是参与者身份。默认 Leader 可以主持，但不同时参赛。同一个底层模型可以运行不同角色，但会话、工具、存储读取权限必须隔离。

如果群 Leader 要参赛，由专门判官身份主持，并从候选主持列表中排除所有玩家。备用判官只能继承判官权限；绝不能把一个已经知道自己身份的玩家临时升级为知道全局身份的判官后继续参赛。

| 信息 | 可见者 |
| --- | --- |
| 公开发言、轮次、存活列表、已公开结果 | 全群 |
| 玩家词语 / 身份 | 判官状态服务、该玩家 |
| 狼人内部讨论 | 当前游戏的狼人频道成员及规则授权的判官 |
| 尚未揭示的投票 | 投票人、判官状态服务 |
| 通用调度状态 | task/phase/slot 等非秘密元数据 |

秘密保存在有独立 ACL 的游戏状态中，给模型输入时按身份投影。隔离不仅覆盖消息，还要覆盖 controller 提示词、模型会话、日志、错误、恢复快照和工具返回。玩家不能拥有读取整个本地游戏数据库的工具；优先使用无文件/终端/浏览器工具的游戏专用会话。无法保证隔离的 CLI 不作为公平游戏验收玩家。

同一真人作为玩家时，UI 也只能给其玩家视图；旁观者模式可以在游戏结束后复盘。不要通过通用应用快照提前把其他玩家的秘密传给该玩家界面。宿主机器管理员仍能访问本地数据，本地模式不承诺抵抗恶意宿主。

Agent 间可私发消息，但由活动规则决定允许的收发关系和阶段；狼人杀不默认允许任意玩家整局私聊。普通协作私信沿用现有权限。升级 Leader 权限不会自动获得全群成员的历史私信。

新增投递语义：`inform` 仅送达信息；`request` 创建需要行动的任务。发身份用 `inform`，轮到发言或夜间行动用 `request`。私信回复继承私信范围，只有明确的公开发言任务才发布到群。

### 7.2 谁是卧底：第一版验收规则

先实现一个固定、版本化变体，避免规则在运行中漂移：4–8 名玩家，恰好 1 名卧底，无白板，无猜词翻盘，判官不参赛。

```text
报名 → 锁定玩家/规则 → 随机分配身份和词语 → 私发并确认送达
→ 逐位公开描述 → 私下收票 → 统一公开计票 → 淘汰
→ 检查胜负 → 下一轮描述 / 最终公布
```

- 词对先由词库或生成模型准备并验证，身份随机分配并保存一次；Jev 不负责随机数或生成词语。检查点恢复不重新发牌。
- 固定座次循环，每位存活玩家每轮一个发言槽。当前玩家的发言成功提交，才放行下一人；后者能读到前者发言。
- 发言期间自由 @ 不创建额外游戏发言。申请插话作为候选请求处理。
- 描述结束后每位存活玩家提交结构化投票 `gameId/round/ballotId/voterId/targetId`；禁止投自己和出局者。单轮每人一票、首次合法提交生效、同键重试幂等。
- 得票最高且唯一者出局；平票者各辩论一次，全体存活玩家在平票候选内重投一次，仍禁止自投。再次平票或全部弃权，使用游戏开始前声明的随机抽签规则淘汰一名候选。随机结果一经保存不得重抽。
- 每次淘汰后先检查卧底是否出局：是则平民胜；否则只剩两人时卧底胜；其余进入下一轮。因每轮必淘汰一人，合法运行最多 N−2 轮达到胜负，不靠模型宣称胜利。
- AI 发言 / 投票失败先有限重试；仍失败分别记为跳过 / 弃权。系统性模型故障暂停。真人未响应默认等待，开局选择了计时玩法才允许超时跳过 / 弃权。
- 全 AI 游戏在一次“开始”后自动运行；有人类玩家时仅在需要其发言或投票时等待，不需要人反复说“继续”。

### 7.3 狼人杀：第二版验收规则

先限定 6 名玩家的简化变体：2 狼人、1 预言家、3 平民，无警长、女巫、猎人、遗言技能。规则开局展示并固定，复杂角色以后扩展。

```text
发身份 → 夜晚狼人讨论/选目标 → 预言家查验 → 程序结算死亡
→ 检查胜负 → 白天依次发言 → 投票/淘汰 → 检查胜负 → 下一夜
```

- 狼人通过仅狼人可见的子频道讨论，轮数有界；各提交夜袭目标，最高票生效，平票按开局约定的随机规则选一名非狼人。保存抽签结果。
- 预言家提交一个存活的其他玩家 ID，规则服务私发阵营结果。夜间行动以夜晚开始时的资格快照收集，统一结算，避免执行先后影响规则；结果是否在当夜被杀后仍送达按此变体固定为送达。
- 白天发言按座次，投票及平票处理复用上面的投票引擎；出局者无发言槽、无投票和夜间行动资格。
- 狼人数为零则好人胜；否则狼人数不少于存活好人数则狼人胜。夜晚结算和白天淘汰后均检查；终态后取消所有未执行游戏任务，胜负只发布一次。
- 判官主持语言可以由 LLM 生成；若主持生成失败，规则服务用模板宣布阶段，不因此停掉已确定的流程。

## 8. 验收矩阵

测试分三层：脚本模型验证协议和状态机；录制案例回放比较 Jev/LLM 路由；真实模型试玩验证语义、中文指代和游戏体验。以下为待实现的验收，不是当前已通过结果。

| 场景 | 必须满足 |
| --- | --- |
| 消息只发给真人 | 无 Agent 任务，不额外发“收到” |
| 单人及多人有序任务 | 成员准确，无重复；后续成员看到前序已提交结果 |
| 群内 50+ Agent | 无逐人唤醒模型；明确对象不因候选筛选被漏掉 |
| 私发身份 | 玩家只看到自己的秘密；投递不自动产生公开发言 |
| 全 AI 谁是卧底 | 一次开始，多轮发言/投票，确定胜负，仅一份最终结果 |
| 真人加入游戏 | 只在其行动槽等待，回复后自动继续；跨私聊回复带活动关联 |
| 平票、弃权、迟到、重复投票 | 按固定规则处理，不能重复计票、永久死循环或修改结算 |
| 狼人私聊 | 平民、通用 Leader/controller、无关成员拿不到正文 |
| Leader / 判官失败 | 合格备用接管相同阶段，不重新发牌、不泄密、不重复淘汰 |
| 旧 Leader 迟到写入 | epoch 校验拒绝，包括旧计划、旧票轮和旧任务结果 |
| 重启、消息乱序、重复事件 | 从检查点恢复；过去的投票不能进入新轮次 |
| Jev 故障 / 关闭 / 低把握 | 自动走兼容路径，相同场景仍能完成 |
| 停止游戏、预算耗尽 | 明确取消或暂停，无后续幽灵发言，不伪造胜负 |
| 远程群权限不足 / 玩家设备离线 | 显式等待权限或设备；不能跳过 owner claim 强行执行 |

记录路由准确率、漏答率、误插话率、平均唤醒 Agent 数、决策 p50/p95、调用成本、回退率、重复结果、完成率和恢复耗时。候选门槛：固定脚本/随机种子下 100 局全部终止且零越权/重复提交；真实模型先跑 20 局评估自动完成率，失败逐局归因，不能用固定阈值或供应商延迟代替实测。

## 9. 实施顺序和代码边界

1. **统一协议**：从 `group.ts` 提取决策 provider；先适配现有 LLM controller，保留已有默认行为。加入 `ignore/wait/finish` 区分、结构化派发和私信 inform/request。游戏范围限制不影响普通协作合法交接。
2. **持久化调度**：在 `store.ts` 增加活动、事件、任务、结果/outbox 与本地恢复；在 `runtime.ts` 接入事件驱动。已有 16 次上限改为单次执行预算，活动自动续调仍受总预算约束。
3. **Jev 可选后端**：新增 `src/main/group/jevDecisionProvider.ts`，配置、凭据、超时、校验、熔断、成本记录；用 `shadow` 评估只记决策不执行，比较后启用 `hybrid`。Jev 不成为游戏上线前置条件。
4. **谁是卧底完整闭环**：新增 `src/shared/activities/undercover.ts`、通用投票引擎、角色可见状态、游戏专用无工具会话，完成全 AI / 真人混合验收。
5. **故障与狼人杀**：增加主持身份恢复和隔离测试，再实现 `werewolf.ts` 与狼人子频道。
6. **远程共享群**：在相邻服务项目增加权威租约、游戏状态、私密投递 ACL、角色投影视图及协议能力协商；沿用设备 claim、owner 权限和 outbox，不另造未经授权的执行通道。需要数据库增量迁移及服务端/桌面一起升级。

兼容按群/活动版本启用：旧群先走现有控制器；新活动走持久化调度。正在运行的活动固定协议和规则版本，切换 Jev 只影响下一次尚未提交的决策；回退不能重跑已完成任务。关闭新功能后保留活动日志和恢复状态，不能静默丢弃未完成活动。

建议优先完成“可靠调度 + 谁是卧底”，同时把 Jev 做成可选优化。这个验收能证明消息、私信、顺序、投票和恢复协议可用；不能据此保证任意开放式任务都能自动规划正确。
